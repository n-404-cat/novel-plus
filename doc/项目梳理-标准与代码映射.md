# novel-plus 项目梳理：标准、文档与代码映射

## 1. 目的

本文档用于对 `novel-plus` 仓库进行结构化梳理，形成以下几类对应关系：

1. 标准和规范类文档与当前代码实现的映射。
2. 需求、技术、部署、生成物与代码目录之间的映射。
3. 当前仓库已经具备的工程化能力与明显缺口。

本文档面向当前仓库实际代码，不是泛化的软件工程说明。

## 3. 项目定位

根据 `README.md`，本项目是一个原创文学 CMS 系统，覆盖：

- 前台门户
- WAP/移动阅读
- 作家后台
- 平台后台
- 爬虫采集管理
- 小说内容存储
- 充值订阅
- 新闻发布
- 统计报表
- AI 辅助创作

从仓库组织看，这不是单体页面项目，而是“多子系统、共享领域模型、共享数据库、部分共享模板资源”的内容平台。

## 4. 工程结构梳理

根工程 `pom.xml` 定义了 4 个模块：

```text
novel-plus
├── novel-common
├── novel-front
├── novel-crawl
└── novel-admin
```

结合代码与构建配置，可归纳为：

### 4.1 `novel-front`

职责：

- 前台门户
- 移动端门户
- 用户中心
- 作家专区
- 充值支付
- AI 写作/生图能力
- 阅读页、目录页、评论页

关键特征：

- Spring Boot 3.4.0 体系
- 提供页面路由和 REST 接口两类能力
- 模板引擎为 Thymeleaf
- 支持多模板目录切换
- 章节内容支持多种存储实现

证据：

- 启动类：`FrontNovelApplication`
- 页面控制器：`controller/page/PageController.java`
- 业务接口控制器：`controller/BookController.java`、`UserController.java`、`AuthorController.java`
- 模板目录：`src/main/resources/templates`
- 静态资源目录：`src/main/resources/static`

### 4.2 `novel-admin`

职责：

- 平台后台管理
- 小说、分类、章节、评论、新闻、友情链接、支付等后台 CRUD
- 统计报表
- 代码生成辅助功能
- 系统权限、菜单、角色、字典等管理

关键特征：

- 独立使用 Spring Boot 2.7.18
- 使用 Shiro 做后台权限体系
- 管理端和前台端不是同一技术代际，存在版本并行
- 使用 ShardingSphere JDBC 接入数据库

证据：

- 启动类：`novel-admin/src/main/java/com/java2nb/AdminApplication.java`
- 后台控制器路径普遍以 `/novel/...` 开头
- `doc/sql/novel_plus.sql` 中存在大量 `sys_*` 表，对应后台系统能力

### 4.3 `novel-crawl`

职责：

- 爬虫源管理
- 规则测试
- 单本采集任务管理
- 自动更新与定时采集
- 磁盘监控与告警

关键特征：

- 独立的 Spring Boot 模块
- 暴露爬虫管理 REST 接口
- 支持规则测试 `testParse`
- 支持采集源启停和单任务进度查询

证据：

- 启动类：`CrawlNovelApplication`
- 控制器：`novel-crawl/src/main/java/com/java2nb/novel/controller/CrawlController.java`
- 配置：`novel-crawl/src/main/resources/application.yml`

### 4.4 `novel-common`

职责推断：

- 提供公共实体、通用工具、公共配置、公共 Mapper 或公共基础设施

说明：

- 本轮未展开深读 `novel-common` 全量代码，但从三个业务模块都依赖它可以判断，它承担的是共享基础层职责。

## 5. 技术栈与分层现状

### 5.1 技术栈

父工程与各模块 `pom.xml` 显示当前项目是“新旧技术栈并存”的状态：

- Java 21
- Spring Boot 3.4.0：前台、爬虫、父工程
- Spring Boot 2.7.18：后台管理
- MyBatis / MyBatis Dynamic SQL / PageHelper
- ShardingSphere JDBC
- Redis / Jedis
- Thymeleaf
- Shiro
- JWT
- Aliyun OSS
- Alipay SDK
- Spring AI
- Docker

### 5.2 典型分层

代码整体符合传统 Java Web 分层模式：

- `controller`：接口层/页面控制层
- `service` / `service.impl`：业务层
- `mapper` 或 `dao`：数据访问层
- `entity` / `domain` / `vo`：数据对象层
- `core/config/filter/utils`：基础设施层

但也存在两个现实问题：

1. 不同模块的命名风格不完全一致。
2. 后台模块与前台模块技术代际不同，后续统一治理成本较高。

## 7. 接口与页面梳理

### 7.1 前台接口

从 `novel-front` 控制器可识别出四类接口：

- `book/*`：小说检索、详情、榜单、评论、目录相关
- `user/*`：登录、注册、书架、阅读历史、反馈、用户信息
- `author/*`：作家和创作相关
- `news/*`、`friendLink/*`、`cache/*`、`pay/*`：配套能力

这说明前台模块同时承担：

- SPA/异步数据接口
- SSR/模板渲染页面

### 7.2 页面路由

`PageController` 说明系统大量页面使用后端模板直出：

- 首页 `/`
- 登录/注册
- 书架/历史
- 书籍详情页 `/book/{bookId}.html`
- 目录页 `/book/indexList-{bookId}.html`
- 章节阅读页 `/book/{bookId}/{bookIndexId}.html`
- 评论页、新闻页、作者页

这意味着：

- 当前前台不是前后端完全分离架构。
- 页面 SEO、静态化风格 URL、模板资源组织是核心实现方式。

### 7.3 管理后台接口

`novel-admin` 控制器体现出典型运营后台特征：

- `/novel/book`
- `/novel/bookContent`
- `/novel/bookIndex`
- `/novel/bookSetting`
- `/novel/author`
- `/novel/news`
- `/novel/category`
- `/novel/user`
- `/novel/pay`
- `/novel/stat`

整体以后台页面 + AJAX 列表接口为主。

### 7.4 爬虫接口

`CrawlController` 体现的核心接口有：

- `addCrawlSource`
- `listCrawlByPage`
- `getCrawlSource/{id}`
- `testParse`
- `updateCrawlSource`
- `openOrCloseCrawl`
- `addCrawlSingleTask`
- `listCrawlSingleTaskByPage`
- `delCrawlSingleTask/{id}`
- `getTaskProgress/{id}`

其中 `testParse` 是爬虫规则治理的关键工具接口。

## 8. 数据库与存储梳理

### 8.1 SQL 文档体系

`doc/sql/readme.md` 已经定义了数据库交付方式：

- `novel_plus_data.sql`：带初始化数据
- `novel_plus.sql`：纯结构
- `yyyyMMdd.sql`：增量升级脚本

这说明项目已经具备“初始化 SQL + 增量 SQL”的版本化交付思路。

### 8.2 章节内容存储

代码中存在 `DbBookContentServiceImpl` 与 `FileBookContentServiceImpl`，可推断章节内容支持：

- 数据库存储
- 文件存储

同时 SQL 中又存在 `book_content0` 到 `book_content9`，结合 `ShardingSphere-JDBC` 可推断：

- 章节内容可能采用分表策略
- 大文本内容存储是专门治理过的

### 8.3 配置与数据源

后台 `application.yml` 中显示：

- 使用 `ShardingSphereDriver`
- 配置位于 `config/shardingsphere-jdbc.yml`

说明数据库分片配置是部署级配置，而非完全内嵌在代码中。

## 9. 构建、部署与生成物梳理

### 9.1 构建方式

根工程为 Maven 多模块工程：

```bash
mvn clean package -DskipTests
```

### 9.2 模块构建产物

`novel-front/pom.xml` 与 `novel-crawl/pom.xml` 中使用 `maven-antrun-plugin` 做了额外打包动作，包括：

- 拷贝配置到 `target/build/config`
- 拷贝脚本到 `target/build/bin`
- 组装 `zip`
- 拷贝 `Dockerfile`
- 前台模块还会同步模板资源到根目录 `templates`

这表明仓库不仅产出 jar，还产出可部署压缩包和模板资源目录。

### 9.3 部署方式

`README.md` 提供了典型部署命令：

```bash
cd /www/wwwroot/novel-plus
mvn clean package -DskipTests
systemctl restart novel-front
systemctl restart novel-admin
```

说明该项目实际运维形态更接近：

- 多服务部署
- 进程级重启
- 非容器优先，但兼容 Docker 交付

## 14. 本轮梳理结论

当前 `novel-plus` 已具备可运行、可部署、可扩展的多模块内容平台形态，但其文档现状更像“代码附带说明”，还不是“按标准组织的软件文档体系”。

如果以 `GB/T 8567-2006`、项目技术文档、需求文档、代码生成文档为目标来整理，本项目最需要做的不是再写一份大而全的 `README`，而是把现有信息拆分为以下四层：

1. 需求层：系统到底解决什么业务问题。
2. 设计层：系统如何分模块、分数据域、分部署单元实现。
3. 实现层：代码目录、表结构、接口、模板、构建产物如何落地。
4. 运维层：如何初始化、升级、部署、回滚、巡检。

本文档是这项整理工作的第一份总览锚点。
