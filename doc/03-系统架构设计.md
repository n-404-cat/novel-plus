# 03 系统架构设计

## 1. 总体架构

当前系统采用多模块、多服务协作架构：

- `novel-front`：面向读者与作者的前台服务
- `novel-admin`：面向运营与管理人员的后台服务
- `novel-crawl`：面向采集与规则治理的爬虫服务
- `novel-common`：公共基础层
- MySQL：核心业务数据存储
- Redis：缓存与会话相关能力

## 2. 服务边界

### 2.1 `novel-front`

- 页面模板渲染
- 读者业务接口
- 作者业务接口
- 支付接口
- AI 接口

### 2.2 `novel-admin`

- 管理后台页面
- 平台运营 CRUD
- 系统管理与权限控制
- 统计报表
- 代码生成辅助

### 2.3 `novel-crawl`

- 爬虫源管理
- 规则测试
- 单本采集任务
- 自动更新任务

## 3. 分层结构

- Controller：接收请求、参数转换、返回页面或结果
- Service：核心业务处理
- Mapper/DAO：数据库访问
- Entity/Domain/VO：数据结构
- Core/Config/Utils：基础设施、配置、过滤器、工具类

## 4. 关键架构特征

- 前台和爬虫使用 Spring Boot 3.x 体系
- 后台使用 Spring Boot 2.7.x 体系
- 后台使用 Shiro
- 前台使用 JWT
- 章节内容支持多实现切换
- 章节内容存在分表设计
- 模板资源独立组织并参与打包

## 5. `R-030` 支付配置架构补充

- `novel-admin` 新增支付配置单页，当前先维护支付宝配置，并负责保存后清理 Redis 缓存
- `novel-common` 新增支付配置共享实体与 Mapper，作为前后台共用的数据结构定义
- `novel-front` 新增支付配置读取服务，请求支付时优先读取数据库配置，配置缺失时回退到本地环境变量兜底
- Redis 新增支付配置缓存键前缀，采用短缓存 + 后台主动失效的组合方式，保证修改后即时生效且缓存异常时可自动恢复
- 支付配置与网站信息拆分存储，避免继续把支付密钥等字段塞入 `website_info`，降低站点基础配置与支付配置的耦合

## 6. 当前架构风险

- 技术栈代际不统一
- 文档与代码的追踪关系尚未完全建立
- 自动化测试材料较少
- 敏感配置示例需要后续治理
