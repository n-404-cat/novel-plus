# 13 研发协作规范

## 1. 总原则

- 先分析，后修改
- 先文档，后代码
- 文档与代码同步交付
- 代码修改必须补中文注释
- 代码修改后必须执行自动化测试与错误检查
- 发现页面、日志、控制台、命令行错误后默认直接修复

## 2. 需求处理流程

### 2.1 新需求

1. 先追加到 `doc/02-需求规格说明.md`
2. 状态先标记为 `待分析`
3. 明确影响模块和目标
4. 方案明确后改为 `待开发` 或 `开发中`
5. 代码完成后改为 `待验证`
6. 完成自动化测试与错误检查后改为 `已验证` 或 `已完成`

### 2.2 已有需求变更

1. 先更新原需求描述
2. 记录变更影响范围
3. 再开始代码调整

## 3. 注释规范

- 对核心业务逻辑补充中文注释
- 对复杂条件、边界处理、兼容逻辑、分表切换、缓存处理补充中文注释
- 避免无意义注释

## 4. 敏感信息规范

- 禁止把真实数据库账号、数据库密码、Redis 密码、API Key、邮件授权码等信息提交到仓库
- 禁止把真实敏感信息写入文档、配置文件、脚本、注释
- 本机开发必须使用私有配置文件、环境变量或启动参数覆盖
- 示例配置只能使用占位符

## 5. 测试与监控规范

- 代码一旦修改，必须执行自动化测试或可执行验证命令
- 涉及页面改动，必须检查页面渲染和交互流程
- 必须检查浏览器控制台错误
- 必须检查应用错误日志
- 必须检查构建、启动、脚本执行时的命令行错误
- 发现错误后默认继续修复，不以“已发现”作为结束

## 6. 提交规范

- Git 提交说明必须使用中文。
- 提交说明需要准确概括本次变更目标，避免使用无意义的 `update`、`fix`、`wip`。
- 涉及需求编号时，优先在中文提交说明中带上需求编号，方便后续追踪。

## 7. 文档同步矩阵

- 需求变更：更新 `doc/02-需求规格说明.md`
- 架构变更：更新 `doc/03-系统架构设计.md`
- 数据变更：更新 `doc/04-数据库设计.md`
- 接口变更：更新 `doc/05-接口设计.md`
- 前台变更：更新 `doc/06-前台模块设计.md`
- 后台变更：更新 `doc/07-后台模块设计.md`
- 爬虫变更：更新 `doc/08-爬虫模块设计.md`
- 部署变更：更新 `doc/09-部署与运维手册.md`
- 测试结果：更新 `doc/11-测试说明.md`
